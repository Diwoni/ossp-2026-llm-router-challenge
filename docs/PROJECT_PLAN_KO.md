# 우승 후보 라우터 개발 계획

## 목표

이 프로젝트는 공개 Dev 점수를 단순히 외우는 라우터가 아니라, 공개되지 않은
평가 프롬프트에서도 정해진 비용을 지키며 높은 품질을 내는 라우터를 목표로
합니다. 성능, 비용 안전성, 실행 안정성, 재현 가능성을 모두 통과한 후보만 최종
제출본으로 채택합니다.

## 반드시 지킬 공식 조건

| 항목 | 기준 |
| --- | --- |
| 라우팅 정보 | 현재 프롬프트 내용과 평가 등급만 사용 |
| 출력 | 문항마다 `ax31-light`, `ax31`, `axk1-think` 중 하나 |
| 최종 점수 | Fast 0.4 + Balanced 0.3 + Premium 0.3 |
| 비용 한도 | Fast 1.25, Balanced 2.0, Premium 4.0 |
| 실행 환경 | `linux/arm64`, CPU 2개, 메모리 2 GiB, 등급별 90초 |
| 격리 | 네트워크·GPU 없음, 읽기 전용 루트 파일 시스템 |
| 금지 정보 | 문항 ID, 입력 순서, split, 비공개 결과와 외부 추론 서비스 |

비용 한도를 아주 조금이라도 넘으면 해당 등급 점수가 0점이므로, 공개 자료에서
한도에 맞추는 것보다 숨은 자료의 비용 변동에도 버틸 여유가 더 중요합니다.

## 개발 단계

1. 공식 baseline과 이전 후보를 같은 평가 코드에서 재현합니다.
2. Train→Dev, Dev→Train, 문제군별 교차검증으로 일반화 성능을 측정합니다.
3. 경쟁 저장소의 좋은 아이디어를 하나씩 독립 실험합니다.
4. 평균 점수뿐 아니라 최악 fold와 비용 스트레스를 통과한 후보만 채택합니다.
5. 최종 후보를 공개 전체 자료로 다시 학습하되 이 점수를 일반화 성능으로
   부르지 않습니다.
6. 공식 자원 제한과 ID·순서 변경 감사에서 최종 이미지를 검증합니다.
7. 코드 커밋, ARM64 이미지 다이제스트, 기술 제출 JSON을 순서대로 고정합니다.

## 점수의 이름을 정확히 구분합니다

| 이름 | 의미 | 최종 평가 예측에 쓰는 정도 |
| --- | --- | --- |
| 홀드아웃 | 학습·선택에 쓰지 않은 분할의 점수 | 가장 중요 |
| 역방향 홀드아웃 | Dev로 학습하고 Train에서 확인한 점수 | 분포 변화 확인 |
| Group K-fold | 같은 문제군을 fold 사이에 섞지 않은 점수 | 문제군 일반화 확인 |
| 공개 재대입 | Train+Dev로 학습한 뒤 같은 자료를 다시 평가 | 회귀 검사만 사용 |
| 스트레스 | 비용·문제군 비율을 인위적으로 흔든 결과 | 예산 0점 위험 확인 |

## GitHub 운영 원칙

- 이슈에는 가설, 비교 기준, 완료 조건을 먼저 씁니다.
- 한 커밋은 한 가지 논리적 변경만 담고 커밋 메시지는 한글로 씁니다.
- 실험 PR에는 실행 명령, 결과 표, 채택 또는 기각 이유를 기록합니다.
- 외부 아이디어는 출처와 라이선스를 기록하고 독립 실험 결과로 판단합니다.
- 실패한 실험도 수치와 이유를 남겨 같은 실수를 반복하지 않습니다.

현재 작업 이슈는 [GitHub Issues](https://github.com/Diwoni/ossp-2026-llm-router-challenge/issues)에서
확인할 수 있습니다.
